# GLM OS

> Экспериментальная 64-битная операционная система, написанная с нуля на Rust `no_std`.

**GLM OS — это эксперимент, в котором вся операционная система создаётся искусственным интеллектом.** Весь код, архитектура, документация, тесты, сценарии сборки и остальное содержимое проекта сделаны **GLM 5.3 Flash от Z.ai** — без контроля, редактирования или построчного руководства со стороны человека.

Проект намеренно публикуется как открытый эксперимент: он показывает, что языковая модель может самостоятельно спроектировать и реализовать минимальное ядро, загрузку, консоль, управление памятью, файловую систему и shell. Это не production-система и не утверждение о пригодности сгенерированного кода для критически важных задач.

## Что это сейчас

GLM OS загружается в 64-битном режиме x86_64 через [Limine](https://limine-bootloader.org/) и запускает собственное ядро на чистом Rust без стандартной библиотеки и runtime-зависимостей.

Текущая реализация включает:

- загрузку ядра ELF через Limine;
- собственный entry point и стек ядра;
- framebuffer-консоль с цветным выводом и bitmap-шрифтом 8×8;
- последовательный debug-вывод через COM1 (`115200 8N1`);
- GDT с сегментами DPL3 и 64-битным TSS (RSP0 + IST1);
- IDT с ручными ISR-стабами на стабильном Rust, вентиль `int 0x80` с DPL3;
- PIC 8259 с переназначением IRQ + Local APIC (виртуальная проводка LINT0=ExtINT, EOI в оба контроллера);
- LAPIC-таймер 250 Гц с калибровкой по PIT — такт планировщика;
- PIT 100 Гц (uptime и курсор) и ввод с PS/2-клавиатуры;
- bitmap physical-frame allocator;
- собственный free-list heap allocator размером 64 MiB;
- собственный менеджер таблиц страниц (PML4/PDPT/PD/PT) с самотестом;
- адресные пространства per-task: пользовательская нижняя половина + разделяемая ядерная;
- вытесняющий round-robin планировщик (вытеснение ring 3, кооперативные ядерные задачи, kidle/kstat);
- **SMP**: подъём всех ядер через протокол Limine MP, per-CPU индексы по LAPIC ID, собственные GDT/TSS и LAPIC-таймер на каждом ядре, привязанные kidle-задачи, миграция задач между ядрами, IPI;
- **сигналы** (v0.5): `sigaction`/`sigreturn`, доставка «хирургией кадра» при возобновлении задачи, страница-трамплин sigreturn в каждом адресном пространстве, SIGTERM/SIGUSR1/SIGUSR2 ловятся, SIGKILL — нет;
- **IPC-каналы** (v0.5): 8 именованных байтовых колец (256 Б), блокирующие `send`/`recv` через протокол «waiter + would-block + retry», rendezvous по ключу;
- **COW fork** (v0.6): системный вызов `fork` — клон адресного пространства копированием при записи; общие кадры считаются референс-счётчиками; массовая смена PTE сопровождается TLB-shootdown IPI (вектор 0x71) с полным сбросом TLB и подтверждением на каждом ядре;
- **Потоки** (v0.7): `clone`/`thread_exit`/`join` — несколько потоков одного процесса исполняются в ОДНОМ адресном пространстве (общий `Arc<AddressSpace>`, один CR3); `set_fs` ставит потоку персональный FS.BASE для TLS; exit главного потока уводит всю группу потоков, включая работающие на других ядрах (die_flag + завершение на собственном kernel-стеке);
- **Сеть** (v0.8): PCI-перечисление конфигурационного пространства, драйвер Intel e1000 (MMIO-окно BAR0 в фиксированной kernel VA, legacy RX/TX дескрипторные кольца, IRQ линии от firmware), стек Ethernet II → ARP → IPv4 → ICMP, kernel-задача `netd` (единый владелец RX-кольца, ARP-кэш с вытеснением, ответы на ARP/echo), команды shell `net`/`arp`/`ping` с TSC-микрометрией RTT; без NIC система продолжает загрузку с предупреждением;
- **UDP-сокеты** (v0.9): userland-сисколлы `net_bind`/`net_sendto`/`net_recvfrom`/`net_close`/`net_info`, таблица из 8 сокетов с очередями датаграмм, loopback-быстрый путь (sendto на собственный IP минует NIC и ARP), сисколл `recvfrom` возвращает адрес отправителя; сигнал будит припаркованные задачи (POSIX EINTR-семантика);
- **Хранилище v1.5 — постоянный диск**: AHCI-драйвер SATA (`src/disk/ahci.rs`: PCI-проба класса 0106 (00:1f.2 на q35), маппинг ABAR, старт порта с публикацией command list / FIS receive / command table из физически непрерывных кадров, IDENTIFY через polled DMA, READ/WRITE DMA EXT чанками по 32 КиБ через общий scratch-буфер) плюс перевод FAT32 на абстракцию `BlockDev` (`src/disk/mod.rs`): рамдиск стал read-only block-устройством, диск — read-write; FAT32 получил полноценную запись — кэш всей FAT в RAM с записью в ОБЕ копии таблицы, аллокация/освобождение кластерных цепочек, создание 8.3-записей с разрешением коллизий (~1), tombstone-удаление 0xE5 вместе с LFN-группой, расширение каталога новыми кластерами, замещающая запись файлов; shell-команды `dstat`/`dls`/`dcat`/`dsave`/`ddel`/`drun`, причём `drun` исполняет ELF64, загруженный С ДИСКА — файлы переживают перезагрузку (проверено двумя загрузками на одном образе);
- **Файлы в ring 3 (v1.6)**: сисколлы 36–42 (`file_open`/`file_read`/`file_write`/`file_close`/`file_seek`/`file_unlink`/`file_list`) поверх дисковой FAT32 — таблица из 16 открытых файлов с цельно-буферной семантикой (open загружает содержимое, close сбрасывает dirty-буфер на диск), флаги O_CREATE/O_RDWR/O_APPEND, упакованный листинг корня, отказ unlink'у открытого файла, auto-close+flush при смерти задачи (exit_current, texit и вытесненные потоки группы); userland `COUNTER.ELF` (счётчик загрузок живёт в /COUNTER.DAT, exit-код = номер бута) и `FILES.ELF` (листинг корня из ring 3, exit = число записей);
- **GUI** (v1.0): драйвер PS/2-мыши (aux-порт 2, IRQ12, потоковый режим) с ISR-декодером 3-байтовых пакетов (sync-бит, знаковые дельты, кнопки, отбраковка мусорных байтов и ресинк) и графический рабочий стол в framebuffer; kstat приостанавливает вывод на консоль, пока GUI владеет экраном;
- **TCP v1.3 — потоковый транспорт в ring 3**: сисколлы 30–35 (`tcp_connect`/`tcp_listen`/`tcp_accept`/`tcp_send`/`tcp_recv`/`tcp_close`), честный handshake (SYN → SYN|ACK → ACK с ретранcмитом SYN раз в секунду и таймаутом 8 с), in-order поток с мгновенными ACK (out-of-order дропается и ре-ACK'ается — пир перешлёт), кольца TX/RX по 8 KiB на сокет, ретранcмит старейших 1400 байт раз в 400 мс из netd-тика (8 попыток → reset), FIN-закрытие, EOF как `recv() == 0`, RST-обработка; блокирующие сисколлы спят в контексте вызывающей задачи (SYS_SLEEP 5 мс, никаких локов при ожидании); TCP-таблица в команде `net`; userland `TCPCLI`/`TCPSERV` — эхо-обмен с host-пиром через slirp в обе стороны;
- **Терминальные окна v1.4 — шелл на рабочем столе**: пункт «terminal» в стартовом меню спавнит kernel-задачу `kterm`, которая открывает собственное окно (скроллбек с посимвольными цветами палитры, живая строка ввода, мигающий карет, очередь клавиш от композитора) и перенаправляет ВЕСЬ свой консольный вывод в окно (`Task.out_win`); программы, запущенные `run` из терминала, наследуют перенаправление (spawn/fork/clone) — их SYS_WRITE-вывод появляется в том же окне; несколько терминалов одновременно, каскадное размещение, `exit` и [×] закрывают окно вместе с сессией, `gui` внутри терминала открывает монитор вместо рекурсивного входа в композитор; текстовый шелл уступает клавиатуру на время GUI (никакого воровства нажатий); **заодно найден и закрыт латентный баг heap-аллокатора (с v0.3!)**: `need` не резервировал запас под выравнивание при align ≤ 16 — payload мог выйти до 7 байтов за конец блока и затереть следующий узел free-list (выстрелило на невыровненных блоках от строк терминала); теперь heap под guard'ами (валидация списка на каждый free, magic в заголовках, lock-free дамп диагностики в COM1);
- **GUI v1.2 — окна ring 3 и resize**: каждое окно имеет resize-grip в правом нижнем углу (press-drag-release, контент перерисовывается вокруг новой геометрии); ring-3 приложения открывают собственные окна через GUI-сисколлы `int 0x80` (`gui_open`/`gui_rect`/`gui_text`/`gui_event`/`gui_geo`/`gui_close`, номера 24–29) — ядро композитит их backing store как любое окно, события (клики в локальных координатах, клавиши, close, resize)queued per-window и опрашиваются приложением; смерть задачи убирает её окна (хук в `exit_current`); стартовое меню запускает ring-3 GUI-приложение (GUIDEMO.ELF) прямо с рабочего стола;
- **GUI v1.1 — двойная буферизация и настоящий таскбар**: вся сцена рендерится в off-screen back buffer (одна кадровая аллокация из кучи), во видимый framebuffer блитятся только грязные прямоугольники, курсор штампуется поверх блитов (буфер сцены никогда не содержит курсор — мерцание и смазы исключены по построению); таскбар как у настоящих ОС: кнопка «GLM» со стартовым меню (запуск окон, перезагрузка и halt прямо с рабочего стола), кнопки открытых окон (клик — фокус/свернуть), трей с LED сетевой активности и часами uptime; два типа окон (системный монитор и about-карточка) с фокусом, z-order, перетаскиванием за титлбар, кнопками свертывания и закрытия; градиентные обои с вотермаркой; счётчик FPS в мониторе;
- ring 3: ELF64-лоадер (PT_LOAD, W^X), пользовательский стек, сигналоподобный kill при fault;
- системные вызовы `write`, `readchar`, `exit`, `uptime`, `getpid`, `yield`, `sleep`, `wait`, `kill`, `sigaction`, `sigreturn`, `chan_open`, `chan_send`, `chan_recv`, `fork`, `clone`, `thread_exit`, `join`, `set_fs`, `net_bind`, `net_sendto`, `net_recvfrom`, `net_close`, `net_info`, `file_open`, `file_read`, `file_write`, `file_close`, `file_seek`, `file_unlink`, `file_list`;

## Важное предупреждение

GLM OS — **экспериментальная и потенциально небезопасная ОС**.

- Не используйте её на рабочем компьютере или с важными данными.
- Запускайте образ только в виртуальной машине, например QEMU.
- Реализация неполна, может содержать ошибки, зависать или повреждать данные.
- Отсутствие человеческого контроля означает, что архитектурные решения, код, тесты и документация не проходили обычную инженерную проверку.
- Проект не претендует на безопасность, стабильность, совместимость или пригодность для реального использования.

## Требования

Скрипт сборки рассчитан на Linux-окружение и использует:

- Rust и Cargo с target `x86_64-unknown-none`;
- `mkfs.vfat` и `mtools` для создания ramdisk;
- `xorriso` для создания ISO;
- Limine binary tools;
- QEMU или другой эмулятор x86_64 для запуска.

`build.sh` содержит пути к инструментам Limine и окружению сборки. На другой машине их может потребоваться изменить.

## Сборка

```bash
./build.sh
```

В результате создаётся образ:

```text
build/glm-os.iso
```

Скрипт выполняет следующие шаги:

1. собирает kernel ELF в release-режиме;
2. создаёт FAT32 ramdisk и копирует в него файлы из `ramdisk/`;
3. формирует загрузочный ISO для BIOS/UEFI через `xorriso`;
4. устанавливает BIOS-загрузчик Limine.

## Запуск в QEMU

Пример запуска ISO:

```bash
qemu-system-x86_64 \
  -cdrom build/glm-os.iso \
  -serial stdio \
  -m 1G -smp 4
```

С постоянным диском (v1.5: `dstat`/`dls`/`dsave`/`drun` заработают; v1.6:
файлы доступны и ring-3 программам через file-сисколлы; файлы переживают
перезагрузку):

```bash
qemu-system-x86_64 \
  -cdrom build/glm-os.iso \
  -drive file=build/disk.img,if=ide,format=raw \
  -boot order=d \
  -serial stdio \
  -m 1G -smp 4
```

`-boot order=d` нужен, чтобы SeaBIOS грузился с CD: его дефолтный порядок
пытается первым загрузиться с HDD и зависает на незагрузочном образе.

После загрузки появится цветной экран GLM OS и приглашение shell:

```text
glm> help
```

Serial-консоль особенно полезна для boot log и отладки ранних стадий загрузки.
Флаг `-smp 4` включает настоящий параллелизм: без него ядро загрузится в
одноядерном режиме (планировщик продолжит работать, AP просто не стартуют).

## SMP в двух словах (v0.4)

Limine сам поднимает все ядра до long mode и паркует их на спин-ожидании;
ядро пишет каждому AP адрес входа (`goto_address`), и оно прыгает в
`ap_entry` с собственным стеком и таблицами страниц ядра. Дальше AP:

1. загружает общую IDT (протокол MP оставляет AP `IDTR=0` — классическая
   ловушка: первый же `int` даёт triple fault, что и случилось при первой
   прогонке и было поймано `-d int`);
2. ставит свою пару GDT/TSS (RSP0 и IST1 на каждое ядро);
3. включает свой LAPIC: спуриозный вектор, LINT0 замаскирован
   (8259-прерывания достаются только BSP), таймер с BSP-калибровкой;
4. засылает `sti` и проваливается в собственную привязанную kidle-задачу.

Планировщик: одна глобальная таблица задач под IRQ-безопасным спинлоком;
последовательность «припарковать → выбрать → пометить Running» атомарна,
поэтому задачу никогда не возьмут два ядра сразу. `current` — per-CPU,
`ps` показывает, на каком ядре задача, `cpu` — состояние всех ядер,
`cpu ipi <n>` проверяет межъядерные прерывания. Спинлоки ядра при захвате
сбрасывают IF и восстанавливают его на выходе — иначе прерывание, севшее
на CPU, уже держащий блокировку, повесило бы машину намертво.

## Сигналы и IPC в двух словах (v0.5)

**Сигналы.** Ядро хранит в каждой задаче битовую маску отложенных сигналов
и таблицу пользовательских обработчиков. `kill`/`kill -9`/`kill -u` из shell
и syscall `kill` лишь ставят бит — реальная доставка происходит в
`post_dispatch`, когда планировщик собирается вернуть задачу на CPU:

1. ядро копирует сохранённый ring-3 контекст в `SigFrame` и пишет его на
   пользовательский стек задачи;
2. кадр перехватывается: `rip` = обработчик, `rdi` = номер сигнала,
   по `[rsp]` лежит адрес страницы-трамплина (`mov eax,10; int 0x80`),
   отображённой в каждое адресное пространство на фиксированном VA;
3. обработчик выполняется в ring 3, его обычный `ret` прыгает на трамплин,
   `SYS_SIGRETURN` читает `SigFrame` со стека и восстанавливает все
   регистры — выполнение продолжается с прерванного места.

SIGKILL обрабатывается до поиска обработчика: задача зомбируется с кодом
128+9, её адресное пространство разрушается, родитель получает код выхода.
Тот же путь — для неперехваченных SIGTERM/SIGUSR*.

**Каналы.** `ipc.rs` держит 8 именованных байтовых колец; `open(key)`
создаёт канал или подключается к существующему по ключу (rendezvous для
незнакомых друг с другом процессов). Блокировка реализована честно для
SMP: задача под блокировкой канала регистрирует себя как waiter и
переводится в состояние `BlockedChan` ДО отпускания IPC-блокировки, поэтому
wake-up невозможно потерять; возвратившийся в ring 3 код получает
сентинел -2 и прозрачно повторяет syscall (обёртки glm-user), а будит его
оппонент, опустошивший/заполнивший кольцо. Порядок блокировок:
IPC -> SCHED.

## COW fork в двух словах (v0.6)

**fork.** Системный вызов `fork` (номер 14) работает только в ring 3.
Ядро строит потомку собственный PML4, но вместо копирования страниц —
двойной апгрейд родителя и потомка до read-only: каждый пользовательский
листовой PTE с правами U|W сбрасывается до RO и помечается программным
битом `PTE_COW` (бит 9 словарной записи, «available to software»);
только-читаемые страницы (.text, трамплин sigreturn) разделяются как есть.
Каждый разделяемый кадр получает +1 в таблице референс-счётчиков
(4 байта на кадр, 1 МиБ .bss). Параллельно ядро копирует текущий
ring-3 interrupt-кадр вызывающей задачи на свежий kernel-стек потомка:
у потомка в `rax` — 0, у родителя — pid потомка; планировщик подхватывает
потомка как обычную готовую задачу.

**Первый write.** Запись в COW-страницу даёт page fault (present + write +
user). Диспетчер прежде чем убивать задачу вызывает `cow_resolve`:
если счётчик кадра > 1 — выделяется новый кадр, 4 КиБ копируются через
HHDM, PTE переписывается на приватную копию с W, счётчик старого кадра
падает; если счётчик == 1 — кадр просто снова становится writable.
`destroy()` адресного пространства вместо `free` вызывает `release`:
кадр освобождается лишь когда последний владелец уходит — двойного
освобождения и утечек нет (в демо: 19 кадров на пространство, 0 разделяемых
кадров после выхода обеих задач).

**TLB shootdown.** После массового понижения прав в родительских таблицах
ядро рассылает IPI вектора 0x71 всем онлайн-ядрам: обработчик на каждом
делает полный сброс TLB (перезагрузка CR3) и подтверждает через атомарный
счётчик; отправитель ждёт ACK с ограниченным спином. Сегодня (одно
адресное пространство = один поток, CR3 перезагружается на каждом
переключении) shootdown — страховка; с появлением потоков в одной
адресной области он станет обязательным механизмом.

**Проверка.** `FORKTEST.ELF`: родитель печатает буфер `COW-ORIGINAL-VAL`,
делает fork, потомок в своём экземпляре переписывает начало на `CHILD`
(берёт COW fault) и выходит с кодом 42; родитель дожидается `wait` и
проверяет свой буфер — нетронут. Под `-smp 4` одновременно гонялись два
forktest (+ два fork), поверх — `busy` ×2 на разных ядрах и IPC-диалог
ping/pong: все коды выхода чистые, кадры возвращаются, изоляция
подтверждена.

## Потоки в двух словах (v0.7)

**Модель.** У каждой задачи появились `tgid` (идентификатор группы потоков =
pid главного потока) и разделяемое адресное пространство: `user_space`
стал `Arc<AddressSpace>` — у процессов он свой, потоки одного процесса
держат один и тот же Arc, поэтому у всех потоков один CR3 и одна physical
страничная таблица. Признак главного потока — `pid == tgid`.

**clone (syscall 15).** Аргументы: `entry` (rip), `stack` (rsp) и `arg`
(в rdi потомку). Ядро выделяет новому потоку собственный kernel-стек,
строит нулевой ring-3 кадр с точкой входа `entry` и копией обработчиков
сигналов, увеличивает счётчик ссылок пространства. Адреса проверяются на
каноничность пользовательской половины. Новый tid возвращается создателю.

**thread_exit (16) и join (17).** Поток умирает сам (`thread_exit`) либо
от сигнала — в зомби, не трогая общее пространство: `Arc::try_unwrap`
успешен только у последнего ушедшего участника группы, и только тогда
выполняется teardown (освобождение идёт через референс-счётчики COW).
`join(tid)` атомарно под SCHED_LOCK: ищет зомби-брата, иначе паркуется в
состояние `BlockedJoin` — код выхода доставляется в сохранённый кадр
ждущего (та же «хирургия кадра», что у wait). Пропуск выхода невозможен:
парковка и сканирование происходят под одной блокировкой.
**Почтовый ящик REAP_LOG.** В v0.6 нашлась латентная гонка: планировщик
лениво собирает зомби, поэтому ребёнок мог исчезнуть из таблицы до того,
как родитель вызвал `wait` — тот парковался навсегда. Теперь каждый зомби
при освобождении записывает (pid, exit_code) в кольцо на MAX_TASKS
записей, а `wait`/`join` после просмотра живых задач заглядывают в него.

**exit процесса.** Выход главного потока терминирует всю группу:
заблокированные братья завершаются сразу, а работающие на других ядрах
получают `die_flag` и умирают на своём следующем прерывании — на своём
kernel-стеке, со своим CR3 (код 143 = 128+SIGKILL). Ядро при этом
сознательно течёт на 4 КиБ за self-exit: `destroy_keep_root` не
освобождает корневой PML4, пока CR3 умирающей задачи может на него
указывать — иначе конкурентный `frames::alloc` мог бы выдать этот кадр
под чужие таблицы страниц.

**TLS (syscall 18).** `set_fs(base)` записывает FS.BASE MSR текущему
потоку; планировщик переписывает MSR на каждом переключении (безусловно —
дешевле отслеживания). Пользовательский поток получает персональный
TLS-блок: `mov rax, fs:[0]` читает своё поле. Первый билд поймал занятный
баг: Rust по умолчанию вправе переставлять поля структуры — компилятор
положил `pad` (32 байта) перед `self_id`, и fs:[0] читал нули; лечится
`#[repr(C)]`.

**Проверка.** `THREADTEST.ELF`: главный поток делает clone ×2, оба
работника крутят ОДИН счётчик (4000 инкрементов каждый) под пользовательским
спинлоком на атомарном обмене — на 4 ядрах это честный параллелизм; между
пачками спят, чтобы `ps` показывал состояние. Каждый работник ставит себе
TLS и сверяет `fs:[0]` со своим номером. Главный поток join’ит обоих:
коды 101 и 102, счётчик ровно 8000 — иначе exit 1. В `ps` во время
работы видна вся семья: PID 7/8/9, одинаковые TGID 7 и PML4 0x96000,
состояния JOIN/SLEEP. Регрессии v0.5–v0.6 (forktest, sigtest, ping/pong)
проходят на Arc-пространствах без изменений.

## Сеть в двух словах (v0.8)

Путь пакета наружу (`ping 10.0.2.2`):

```
shell: ping -> arp_resolve(10.0.2.2)          (кэш? нет -> broadcast ARP request, 5 попыток)
       -> icmp_echo_put(type=8, id=0x474C, seq) + checksum
       -> ipv4_put(src=10.0.2.15, dst, proto=1, ttl=64) + header checksum
       -> eth_put(dst=gw MAC, type=0x0800)
       -> e1000::send_frame: копия в TX-буфер слота, дескриптор
          (EOP|IFCS|RS), TDT++, ожидание бита DD (готово)
```

Путь обратно: e1000 DMA-пишет кадр в RX-буфер и ставит DD в дескрипторе,
IRQ 11 -> вектор 0x2B -> ISR считает событие (ICR читается = очищается) и
выходит; кадр из кольца вынимает ТОЛЬКО `netd` под NET_LOCK на своём
5-мс тике. Это осознанное решение: внешний IRQ через PIC всегда
доставляется на BSP (LINT0=ExtINT), и если бы ISR попытался взять
NET_LOCK, удерживаемый прерванной задачей того же ядра, вышел бы
классический deadlock. ISR, который только читает MMIO и увеличивает
атомарные счётчики, не может встать в тупик никогда.

netd разбирает кадры вне блокировок (копия на стеке): ARP-запросы
на наш IP отвечают, ARP-ответы/запросы пополняют кэш (8 слотов,
вытеснение по возрасту), ICMP-запросы получают echo-reply, ICMP-ответы
нашего id попадают в слот для `ping`. RTT меряется TSC, откалиброванным
один раз при старте netd (uptime PIT имеет шаг 10 мс — слишком грубо).

Без NIC (`-nic none`) загрузка продолжается: `[warn] net: no intel
e1000 ...`, команды `net`/`arp`/`ping` сообщают об offline.

## UDP-сокеты в двух словах (v0.9)

В v0.8 сеть принадлежала ядру: `ping` работал из shell-задачи, а весь
приём — внутри `netd`. В v0.9 транспорт впервые вынесен в ring 3:
пользовательская программа связывается с портом, отправляет и принимает
датаграммы через `int 0x80`.

```
UDPSERV.ELF                          UDPCLI.ELF
  bind(7777)                            bind(7778)
  recvfrom(0, buf, &src)  <- очередь <- sendto(1, 10.0.2.15:7777, msg)
  sendto(0, src, msg)     -> очередь -> recvfrom(1, buf, &src)
  ... пока SIGTERM не закроет сокет     verify == msg, x3, exit 0
```

Блокирующий приём работает по протоколу IPC-каналов: recvfrom при пустой
очереди регистрирует задачу как waiter сокета, помечает её `BlockedSock`
ПОД SOCK_LOCK (проснуться без потери никто не может) и возвращает -2;
glm-user прозрачно повторяет сисколл. Когда датаграмма попадает в
очередь (из demux netd или по loopback), waiter переводится в Ready.

Loopback — «сетевой стек внутри одной машины»: `sendto` на собственный
IP вообще не доходит до NIC и ARP — датаграмма сразу ставится в очередь
сокета-получателя. Два ring-3 процесса общаются друг с другом через
настоящий L3/L4-путь (UDP + IPv4 + checksum), без эмуляции проводов.

Демо закрывает и латентный баг, живший с v0.5: `send_signal` только
ставил флаг sig_pending и ждал «возобновления» задачи — но задача,
припаркованная в recvfrom/chan_recv/блокирующем вводе, сама не
возобновится никогда, и сигнал зависал навсегда. Теперь сигнал будит
припаркованные задачи (BlockedInput/Chan/Sock/WaitingChild/Join →
Ready), доставка происходит в post_dispatch, а разбуженная операция
перепроверяет своё условие — POSIX EINTR-семантика. `kill` припаркован
ному эхо-серверу больше не вешает его: обработчик SIGTERM закрывает
сокет, retry-цикл recvfrom видит -1 и сервер выходит с кодом 0.

## TCP в двух словах (v1.3)

v1.3 добавляет третий транспорт в стек: поверх Ethernet/ARP/IPv4 (v0.8)
и UDP-сокетов (v0.9) теперь работает TCP — тот же `int 0x80`, номера
30–35. Ядро держит таблицу из 8 сокетов под `TCP_LOCK`; netd —
единственный RX-потребитель (ISR не трогает TCP вовсе), а
ретранcмит-таймеры едут в его 5-мс тике.

```
ring-3 (TCPCLI/TCPSERV)      ядро (net/tcp.rs)
  tcp_connect(10.0.2.2:7300)   SYN -> SYN|ACK -> ACK (1 c ретранcмит)
  tcp_send(msg)                TX-кольцо -> сегмент -> ждёт ACK
  tcp_recv(buf)                RX-кольцо <- in-order + мгновенный ACK
  tcp_close(id)                FIN -> слот свободен
```

Упрощения задокументированы честно: нет congestion control, SACK и
probe-окон; полный RX-кольцо принимает что влезает и ре-ACK'ает
(пир перешлёт хвост); close шлёт FIN один раз без TIME_WAIT; TCP
loopback'а нет (сокеты идут только через провод). Блокирующие
connect/accept/recv спят в контексте вызывающей задачи — они никогда
не держат лок при ожидании, а все отправки сегментов делаются ПОСЛЕ
сброса `TCP_LOCK` (ARP внутри send_seg спит).

## Хранилище в двух словах (v1.5)

До v1.5 всё, что видела ОС, жило в read-only рамдиске — Limine-модуле, зашитом в ISO при сборке. v1.5 добавляет классический путь настоящих ОС: блочное устройство + файловая система поверх него.

- **`src/disk/mod.rs` — `BlockDev`**: единственный контракт «устройство ↔ файловая система»: `read_sectors`/`write_sectors` (512-байтовые секторы), `sector_count`, `writable`. Две реализации: `RamBlock` (рамдиск Limine — чтение) и `Ahci` (SATA-диск — чтение и запись). FAT32 не знает, где под ним память, а где железо.
- **`src/disk/ahci.rs` — драйвер AHCI**: PCI-перебор шины с учётом ФУНКЦИЙ (контроллер ICH9 q35 сидит на 00:1f.2 — function 2; наивная проба только function 0 его не находит), подъём BAR5 (ABAR) в фиксированную kernel-VA с NO_CACHE, GHC.AE, выбор первого реализованного порта с `PxSSTS.DET == 3` и сигнатурой ATA (ATAPI сознательно пропускается). Для порта: остановка движка, публикация command list (1 КиБ), FIS receive area и command table — физически непрерывные кадры из фрейм-аллокатора, доступ через HHDM; запуск `FRE|ST`. Команды — slot 0: H2D Register FIS (раскладка байтов как в Linux `ata_tf_to_fis`: **device/LBA-селект в байте 7, а не 4** — за этим скрывался первый баг: с неверным раскладом QEMU уходил в CHS-геометрию и «LBA 0» читал сектор 63), один PRDT-элемент на чанк ≤ 32 КиБ, завершение по опросу `PxCI` (IRQ сознательно выключены — блочный слой держит спинлок, MSI-путь можно добавить позже, не трогая FAT32). IDENTIFY даёт модель и LBA48-объём.
- **`src/fs/fat32.rs` — FAT32 read-write**: при монтировании читается вся первая FAT в кэш (`Vec<u32>`; ~512 КиБ на 64 МиБ диск) — все проходы по цепочкам бьют в кэш, каждая мутация переписывает затронутый сектор в ОБЕ копии FAT. Запись: `write_file` (создать или заместить: освобождение старой цепочки, новая цепочка под данные с нулевым хвостом, обновление dirent), `delete` (освобождение цепочки + tombstone 0xE5 на сам dirent и его LFN-группу), аллокация кластеров сканом кэша FAT, расширение каталога свежим обнулённым кластером. Имена пишутся в классическом 8.3 (верхний регистр, санитизация, суффикс ~1 при коллизии); чтение по-прежнему понимает LFN.
- **Shell**: `dstat` (устройство + FS-статистика), `dls`, `dcat`, `dsave <ram> <disk>` (копия из рамдиска на диск), `ddel`, `drun <elf>` — чтение ELF из диска и запуск через `spawn_user_elf_bytes`. Файлы на диске переживают перезагрузку: тест грузит ОС дважды на одном образе и исполняет программу, сохранённую в первой загрузке.
- **Сборка/запуск**: `build.sh` создаёт 64 МиБ `build/disk.img` (FAT32, засеянный тем же BIN-набором + README.TXT), QEMU подключает его к ICH9-AHCI; для glmq-драйвера — `-drive file=...,if=ide,format=raw -boot order=d` (иначе SeaBIOS по умолчанию пытается грузиться с HDD и зависает на незагрузочном образе).

## Файлы в двух словах (v1.6)

До v1.6 постоянным диском владело только ядро: d-команды шелла. v1.6 открывает его ring 3 — обычный `int 0x80`, номера 36–42: любая userland-программа теперь хранит свои данные между загрузками.

- **`src/fs/sysfile.rs` — открытые файлы**: таблица 16 слотов под глобальным `SYSFILE_LOCK` (форма как у `net::sock`); слот = владелец-pid, имя, буфер, курсор, dirty. Модель честная и простая: open загружает содержимое файла в heap-буфер (как делает dcat), read/write двигают курсор, close сбрасывает dirty-буфер через `fat32::write_file`. Флаги: O_CREATE (1) — создать-или-обрезать, O_RDWR (2) — открыть с содержимым и патчить на месте, O_APPEND (4) — курсор в конец; read-only (0) требует существования файла.
- **Границы и защита**: имя ≤ 32 байта печатаемых символов без `/` (путей нет — только корень диска), файл ≤ 256 КиБ, один сисколл ≤ 8 КиБ; user-указатели копируются через translate+HHDM постранично (плохой указатель — Err, а не fault); unlink отказывает, если файл кем-то открыт; ничто из ring 3 не разыменовывается напрямую.
- **Смерть задачи не теряет данные**: `sysfile::on_task_exit(pid)` в `exit_current` (а также в пути texit и для потоков группы, добитых при выходе процесса) закрывает слоты владельца и сбрасывает dirty — упавший с открытым файлом процесс не оставляет ни утечки слота, ни несброшенных байтов. Вызывается после снятия SCHED_LOCK (порядок локов SCHED → SYSFILE → DISK, никогда наоборот).
- **`file_list`** отдаёт корень диска упакованными записями `[kind][len][имя][size u32 LE]`; парсер user-библиотеки (`file_record`) ходит по буферу без alloc — glm-user остаётся freestanding.
- **Userland-доказательство**: `COUNTER.ELF` читает `/COUNTER.DAT`, печатает «boot #N», пишет N+1 и выходит С КОДОМ N — серийный лог (`exited with code N`) машиночитаем: boot 1 → код 1, boot 2 на том же диске → код 2. `FILES.ELF` листит корень и выходит с числом записей — тест проверяет cross-visibility: `dsave`/`ddel` ядра немедленно видны ring 3, и наоборот.

## GUI в двух словах (v1.2)

До v1.0 GLM OS разговаривала с пользователем только текстом. В v1.0 ОС
получила указатель и рабочий стол, в v1.1 — двойную буферизацию и
панель задач как у настоящих ОС, а в v1.2 — окна стали динамическими:
ядро-композитор принимает окна от ring-3 приложений (GUI-сисколлы), а
каждое окно получило resize-grip. Команда `gui` отдаёт framebuffer
графическому режиму, `Esc` или закрытие всех окон возвращает текстовую
консоль.

```
mouse (PS/2, irq12)            gui-цикл (shell-задача, ~50 fps)
  3-байтовый пакет               take() -> дельты, кнопки
  sync bit3 | знаки 0x10/0x20    курсор += clamp(dx,dy)
  кнопки 0..2                    грязные прямоугольники -> back buffer
  ATOM ONLY (урок v0.8)          blit -> фронт -> штамп курсора
```

ISR мыши — только декод в атомики (никаких блокировок в прерывании —
урок сетевого deadlock'а v0.8); GUI-задача забирает накопленное раз в
кадр через SYS_SLEEP, поэтому остальные задачи и IRQ живут как жили.

**Двойная буферизация (v1.1).** Вся сцена (градиентные обои + вотермарка,
окна в z-порядке, таскбар, стартовое меню) рисуется в off-screen
back buffer — одну кадровую матрицу u32 в родном формате пикселей
фреймбуфера резервируем из кучи через `try_reserve_exact`. Каждый кадр
во видимый framebuffer блитятся только грязные прямоугольники
(`Console::blit_from` — copy_nonoverlapping по строкам с обрезкой), а
курсор штампуется ПОСЛЕ блитов: буфер сцены никогда не содержит
курсор, поэтому перемещение указателя = блинт старого региона из
back-буфера (стирание бесплатно) + штамп спрайта на новом месте.
Никаких save/restore-массивов, мерцание и смазы исключены по
построению. Композиция любого прямоугольника идентична (десктоп →
окна → таскбар → меню), поэтому частичная перерисовка не может
разъехаться с полной.

**Таскбар (v1.1).** Внизу — панель как у настоящих ОС: кнопка «GLM»
со стартовым меню (system monitor, about, разделитель, reboot, halt —
с hover-подсветкой и цветными иконками), кнопки открытых окон
(клик по активному сворачивает, по свернутому/неактивному —
восстанавливает и поднимает), справа трей: LED сетевой активности
(сравнение счётчиков rx+tx раз в секунду) и часы uptime. Окна имеют
фокус (синий титлбар) и z-order (активное рисуется последним), кнопки
«−»/«×» в титлбаре. Выбор «reboot» в меню уходит в reset через
ACPI-регистр 0xCF9 (фолбэк — классический 8042-pulse), «halt» —
рисует прощальный экран и засыпает навсегда. Текстовая консоль всё
это время живёт в статическом теневом буфере ячеек — по выходу из
GUI `redraw_all` восстанавливает экран пиксель-в-пиксель. `kstat` на
время GUI печатает только в serial-лог.

**Окна ring 3 (v1.2).** Десктоп — это теперь композитор: кроме двух
kernel-окон (монитор, about) он принимает пользовательские окна.
Ring-3 процесс вызывает `gui_open(title, x, y, w, h)` (сисколл 24) и
получает id своего окна; рисует `gui_rect`/`gui_text` (26/27) в
ОКОННЫХ локальных координатах (ядро пишет прямо в per-window backing
store под GUI_LOCK); опрашивает ввод `gui_event` (28) — packed
события EV_CLICK/EV_KEY/EV_RESIZE/EV_CLOSE с двумя 16-битными
аргументами; спрашивает геометрию `gui_geo` (29) и закрывает окно
`gui_close` (25). Композитор блитит backing store как слой окна:
drag/минимизация/z-order/таскбар работают для чужих окон так же, как
для своих. Resize-grip меняет размер ЛЮБОГО окна; backing store
пользовательского окна пересоздаётся под новый контент, приложению
уходит EV_RESIZE — оно перерисовывается. Гарантии целостности: окно
принадлежит создавшему pid (чужие сисколлы получают -1), смерть
задачи убирает её окна (хук `gui::on_task_exit` в `exit_current`),
блокировка GUI_LOCK → CONSOLE → SERIAL нигде не образует цикла.
Демо: `GUIDEMO.ELF` — ring-3 анимация (мяч + счётчик кадров +
перекраска по клику), запускается из стартового меню пунктом
«run ring-3 demo».

## Тестирование

В репозитории нет отдельной пользовательской тестовой инфраструктуры или полноценного набора integration-тестов: проект — ранний bare-metal эксперимент. Проверки выполняются через сборку, загрузку образа и наблюдение за boot log/поведением в эмуляторе.

Как и весь проект, существующие проверки, сценарии сборки и документация созданы **GLM 5.3 Flash от Z.ai без контроля человека**. Поэтому результаты следует рассматривать как экспериментальные, а не как гарантию корректности.

## Статус

Текущая версия — `v1.6.0`: файловые сисколлы ring 3 — userland-программы читают и пишут постоянный диск, их данные переживают перезагрузку (COUNTER.ELF: exit-код = номер бута, вычитанный из своего файла) — поверх хранилища v1.5 (AHCI SATA + read-write FAT32), терминальных окон v1.4, TCP в ring 3, resize-окон и всего стека ring-3 GUI.
